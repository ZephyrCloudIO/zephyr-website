# EmDash maintenance guide

This site runs server-rendered Astro on Cloudflare Workers. EmDash uses D1 for content and authentication, R2 for uploaded media, and the Astro adapter's session KV binding. Repository-owned React components still control the marketing pages and visual design.

## Local development

Use the version of pnpm in `package.json`. Run `pnpm install`, then `pnpm dev`. On a fresh local D1 database, visit `http://localhost:4321/_emdash/api/setup/dev-bypass` once to import the migration seed. EmDash restricts this bypass to development builds. Do not use it as a production authentication mechanism.

The CMS admin is at `/_emdash/admin`. Local database and uploads persist in `.wrangler/`, which is ignored. Never commit `.dev.vars`, credentials, session tokens, or local database files.

## Content ownership

Editors create and publish blog posts and changelog entries in EmDash. Public routes query the live database, so publishing, unpublishing, or changing a post updates both its article and its listing without rebuilding. Anonymous requests show published entries. Signed EmDash previews can render drafts.

`src/content/blog/` and `src/content/changelog/` are archived migration inputs. `pnpm emdash:prepare` regenerates `.emdash/seed.json` and `.emdash/migration-manifest.json`, copies referenced assets to `docs/public/content/`, and generates the marketing route and enabled lander registries. Seed content is imported only during setup or an explicit seed operation. Rebuilding does not overwrite editorial changes in D1.

The seed defines 27 blog posts and 32 changelog entries, preserving their filename-based URLs, original publication dates, author metadata, topics, and images. Normal content uses Portable Text. Imported HTML uses EmDash's sanitized HTML block. The release-path film and figures have allowlisted React renderers. Installation tabs remain keyboard-accessible; without JavaScript, all instructions remain visible.

Do not edit `.emdash/seed.json` by hand. Make migration corrections in the converter or original MDX and run preparation and verification. For schema changes after setup, use EmDash's collection administration or an explicit supported schema migration; an existing database does not reapply a changed seed.

## Marketing pages and landers

Keep marketing page UI in `src/routes/` and register metadata in `src/data/site-pages.json`. Register its component in `src/components/pages/SitePage.tsx`. Do not put contributor documentation under `src/pages/` or `docs/public/`.

Create a campaign with `pnpm create-lander <slug>`. The component name must remain `<PascalCaseSlug>LanderPage`, as generated by the template. This registers its metadata automatically. Enable it through `ZE_PUBLIC_ENABLED_LANDERS=<slug> pnpm dev` or `ZE_PUBLIC_ENABLED_LANDERS=<slug> pnpm build`. Disabled landers are excluded from the generated registry, public routes, browser bundle, and sitemap.

React asset imports under `@/images/` retain their original URL-string contract through the scoped Vite adapter. Relative asset imports should use `?url`. Astro components should use normal Astro assets outside that compatibility alias.

## SEO and security

`Base.astro` uses EmDash's page context and head/body contribution components for titles, descriptions, canonical links, social cards, structured data, and plugin contributions. Articles honor editor-owned SEO overrides. Marketing metadata remains repository-owned. Every page retains a fallback social image.

The sitemap queries live published content and excludes disabled landers. Public static discovery files still live in `docs/public/`. Keep PostHog as the only analytics provider; do not add Google Analytics or GTM.

Cloudflare's `_headers` file covers static assets, not Worker-rendered responses. `src/middleware.ts` applies the existing public security policy to server responses as well. EmDash admin and API responses retain EmDash's own header handling.

## Validation and deployment

Run `pnpm emdash:prepare`, `pnpm emdash:validate`, `pnpm emdash:verify`, `pnpm typecheck`, `pnpm build`, and `pnpm deploy:dry`. For runtime checks, initialize local content and run `pnpm emdash:verify-runtime`. Add `http://localhost:4321 --cms-writes` to exercise local draft isolation, publishing, unpublishing, and live listing updates. The write check refuses non-loopback destinations and moves its temporary entry to CMS trash afterward. Inspect the home page, blog search, article content, changelog, disabled campaign 404s, and admin in the browser at desktop and mobile sizes.

`pnpm emdash:verify --clean-checkout` copies the Git candidate to a temporary directory, omits ignored generated output, and verifies that preparation and content checks succeed there. CI runs this regression check as well.

Build and dry-run commands never deploy. To deploy intentionally, authenticate Wrangler against the intended account and run `pnpm run deploy`. The `run` selects this repository's script instead of pnpm's built-in workspace packaging command. The configuration deliberately has no production custom domain or copied account identifiers. On a fresh Worker, finish the admin setup wizard and choose the migration seed content before evaluating the public site. For later upgrades, inspect the emitted `.emdash/migrations.json` and follow the installed EmDash CLI's migration requirements before production rollout.

Verify all existing URLs and CMS authentication on the new Worker before moving the production domain. Provisioning, domain cutover, production import, and live validation are separate actions from a successful local build.
